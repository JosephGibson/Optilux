# Standing prompts
Status: the Plan and Release prompts every milestone uses, printed by `optilux status` with the milestone filled in, and the form of the phase prompts the Plan prompt writes.

## Rules
- `## Plan` and `## Release` each hold one `- Estimate: <h> h.` line, which sizes it S/M/L/XL, and one fenced block holding the prompt. `## Phase prompts` is read by the Plan prompt and optilux-plan, never printed.
- `optilux status` prints Plan when the milestone has no prompt set (prompts/m<N>.md), or when the set starts at the phase after the next one (the plan phase in progress), and Release when every phase of the set is done and origin/main carries another VERSION; after the merge it prints the switch block and the next milestone's Plan (workflow.md#running-a-milestone).
- Placeholders, filled in by `optilux status`: {M} the milestone's number (2), {PREV} the previous milestone's number, {PHASE} the phase the Plan prompt completes (M2.P00), {VERSION} the version the milestone ships as, the minor after origin/main's (workflow.md#release).
- Like every stored prompt, these are handed out verbatim and changed only in a commit, never per session.

## Phase prompts
The form of docs/prompts/m<N>.md from M2 on. M0's and M1's sets are history in the old form (0.MM.PP IDs, fixed commit subjects, a Status line edit per phase), which this replaces.
- Format: `# M<N> prompts`, its Status line and Contents (checked by `verify docs`) and a `## Rules` citing this section before the first phase; then what `optilux status` parses (optilux/prompts.py): one `## M<N>.P<PP> <title>` heading per phase from M<N>.P01, ascending, each followed by exactly one fenced block, and `## Resume` last, with one. The parser also takes a 0.MM.PP ID as the same phase; write M<N>.P<PP>. A wrong prompt is fixed in a commit, never rewritten per session.
- A phase prompt stands alone. Its first line: ``Run M<N> phase M<N>.P<PP> on branch m<N> in C:\Projects\Optilux. Take `date` first, for the report. Why: <why>. Done when: the Exit of phase M<N>.P<PP> in docs/plans/m<N>.md holds, shown with output from this session.`` Then what to read by path and heading (not AGENTS.md, which loads with the session); the launches, each announced, what may write runtime/, no system settings; the start gate (branch m<N>, tree clean, tests and verify docs green, or stop); the stops (the plan's section 7, a Done-when it cannot meet) and the unattended default (the plan's recommendation, or the question logged in docs/handoff.md; nothing beyond this phase) in one sentence. Then numbered steps: the change as the plan states it; the tests; a reviewer-agent pass before the phase's first commit where a launch or the mod carries the risk; tests green, ruff and pyright clean, verify docs passes; the docs the change touches; the commits; the Report.
- Commits (workflow.md#git): a phase takes one or more, and its prompt says what each holds, never its subject, which is written when the commit is made and names no milestone, phase, version or date. Each is test-green and pushed with CI green. The phase's last one overwrites docs/handoff.md as the plan's section 9 says (what passed, failed and deferred, commits and time against estimates with the milestone's actuals, questions, the next command), its `Last phase:` line naming the phase. A phase that changes what the milestone delivers extends its `## <version> <Name>` entry in CHANGELOG.md, the release body (workflow.md#release). No phase edits VERSION (the Plan prompt set it) or a Status line to mark progress (workflow.md#doc-ownership).
- Report: the outcome first; each claim backed by output from this session, anything failed, skipped or unverified named; the time since the first `date` against the phase's estimate.
- Resume: `date` first; docs/handoff.md, the roadmap's M<N> section and the plan read; `uv run optilux status` names the last phase (the handoff's `Last phase:` line), the commits since it, the tree and the next prompt, followed verbatim from its first step not done, judged from the tree, the tests and the records, never from memory. A game left running is quit first; an unpushed commit is pushed; a failing test is fixed inside the phase. A test-green commit may hold part of a phase, but the one that writes its `Last phase:` line follows only its whole Done-when shown in this session (a launch's exit included: runtime/ leaves nothing in the tree). Each prompt's named stops and the plan's section 7 still apply. Phase by phase until the last one is committed, then stop with the report: the Release prompt is mine. At any stop, docs/handoff.md overwritten (`Last phase:` naming the last phase completed) and a report.
